# 1. Назначение системы

Система предназначена для долговременной фиксации бытовой визуальной истории пользователя и последующего восстановления контекста событий, связанных с предметами, документами и их перемещениями.

Основная задача — отвечать на естественные вопросы пользователя, например:

* «Где моя отвёртка с жёлтой ручкой?»
* «Куда я положил ключи?»
* «Где я последний раз видел зелёную папку?»
* «Куда я положил документы на сад?»
* «Откуда появилась эта канистра?»
* «Когда я это купил?»
* «Откуда я это достал?»
* «Когда я принёс эту коробку сюда?»
* «Что я делал с этим предметом вчера?»

Система должна работать на горизонте хранения **не менее 1–2 лет**, с возможностью дальнейшего увеличения срока.

Ключевой принцип:

> Система не обязана заранее полностью понимать каждый кадр. Она должна сохранить достаточно исходных данных и поисковых индексов, чтобы нужный эпизод можно было восстановить задним числом.

---

# 2. Основные архитектурные принципы

## 2.1. Local-first

Основной архив, embeddings, OCR, база данных и поиск находятся на домашнем сервере.

Интернет не должен быть обязательным для базового функционирования.

При отсутствии интернета пользователь всё равно должен иметь возможность:

* искать предметы;
* получать найденные кадры;
* видеть время последнего/первого появления;
* просматривать эпизод вокруг найденного момента.

Облачная VLM используется только как дополнительный интеллектуальный слой.

---

## 2.2. Разделение ролей

### Смартфон

Смартфон является прежде всего:

**носимым сенсором и клиентом системы.**

Он отвечает за надёжную фиксацию визуальных данных.

### Домашний сервер

Сервер является:

**долговременной памятью, вычислительным узлом и поисковой системой.**

### Внешняя VLM

Внешняя VLM используется:

**только для анализа небольшого количества уже найденных релевантных кадров/эпизодов.**

# 5. Функции смартфона

## 5.1. Запись

Android-приложение должно иметь максимально простой пользовательский интерфейс.

Основные состояния:

* запись выключена;

* синхронизация;
* ошибка;
* недостаточно памяти;
* критически низкий заряд.

Основной пользовательский сценарий:

```text
утром
↓

↓
носить смартфон
↓
вечером
↓

```

# 6. Режим съёмки

Начальная конфигурация MVP:

**один кадр приблизительно каждые 2 секунды.**

Параметр должен быть конфигурируемым.

Необходимо экспериментально проверить:

* 1 секунда;
* 2 секунды;
* 3 секунды;
* 5 секунд.

Главный критерий — вероятность поймать событие:

```text
взял предмет
↓
перенёс
↓
положил
```

При 16 часах записи и интервале 2 секунды получается примерно:

**28 800 кадров в сутки.**

# 8. Локальное хранение телефона

Файлы организуются по дням:

```text
/records/
    2026-09-09/
        frames/
        metadata/
        manifest.json
```

Каждый день имеет manifest с:

* количеством кадров;
* диапазоном времени;
* контрольными суммами;
* статусом синхронизации.

После успешной загрузки на сервер файлы не удаляются немедленно.

Удаление происходит только после получения подтверждения сервера:

```text
uploaded
+
checksum verified
+
committed to archive
```

---

# 9. Работа при плохом интернете

Для передачи на домашний сервер внешний интернет не требуется.

Смартфон ищет локальный сервер через домашнюю сеть.

Сценарий:

```text
появился домашний Wi-Fi
+
телефон подключён к зарядке
+
сервер доступен
↓
начать синхронизацию
```

Передача должна:

* поддерживать продолжение после обрыва;
* быть идемпотентной;
* не загружать один и тот же файл повторно;
* проверять checksum;
* продолжаться после перезапуска приложения.

---

# 10. Что смартфон НЕ обязан делать

Для первой версии смартфон не должен:

* рассчитывать финальные image embeddings;
* выполнять тяжёлый OCR;
* запускать VLM;
* строить глобальную историю объектов;
* поддерживать многолетнюю базу.

Это сознательное решение.

Качество обработки не должно ухудшаться ради ограничений мобильного железа.

---

# 11. Сервер: ingestion

После получения файлов сервер:

1. принимает manifest;
2. проверяет целостность файлов;
3. рассчитывает checksum;
4. регистрирует кадр в БД;
5. сохраняет оригинал;
6. добавляет кадр в очередь обработки.

Повторная загрузка того же файла не должна создавать дубликат.

---

# 12. Хранение оригиналов

Исходный материал рассматривается как **доказательный архив**.

Он сохраняется даже после создания embeddings.

Причина:

через год может появиться новая модель, способная лучше понять старый эпизод.

Пример:

```text
2026:
модель не поняла происхождение предмета

2028:
пользователь спрашивает
«Откуда появилась эта вещь?»

↓
находим ранние изображения
↓
достаём оригинальный архив
↓
повторно анализируем новой моделью
```

# 15. Blur detection

Каждый кадр получает:

```text
blur_score
quality_score
```

Совсем бесполезные изображения можно исключать из основного поискового индекса.

Однако оригинал желательно некоторое время сохранять.

Нельзя автоматически удалять кадры только потому, что алгоритм считает их неинтересными.

---

# 16. Deduplication

Необходимо определять практически одинаковые изображения.

Используются:

* perceptual hash;
* visual similarity;
* scene difference;
* timestamp.

Пример:

```text
100 кадров телевизора
↓
1–3 keyframes
```

Это значительно сокращает объём inference.

---

# 17. Scene segmentation

Кадры объединяются в эпизоды:

```text
scene_id
start_time
end_time
frames[]
```

Пример:

```text
17:32:10–17:32:50
работа возле шкафа

17:32:51–17:34:20
ходьба по коридору
```

Scene является одним из основных уровней временного поиска.

---

# 18. Visual embeddings

Для визуального поиска используется единая canonical embedding model.

Модель выбирается экспериментально.

Ключевое требование:

> качество модели не должно снижаться только ради возможности запуска на смартфоне.

Одни и те же:

* веса;
* preprocessing;
* resolution;
* precision

должны использоваться при повторной обработке.

Версия модели обязательно сохраняется:

```text
embedding_model
embedding_version
preprocessing_version
```

---

# 19. Поиск мелких предметов

Нельзя полагаться только на embedding уменьшенного полного кадра.

Например, отвёртка в изображении 4000×3000 после уменьшения до 224×224 может практически исчезнуть.

Поэтому система должна поддерживать:

```text
whole-frame embedding
+
crop embeddings
+
object/ROI embeddings
```

Но crops не следует без необходимости рассчитывать для абсолютно каждого кадра.

Предпочтительная стратегия:

### Каждый важный keyframe

whole-frame embedding.

### Интересные изображения

несколько пространственных crops.

### Предмет в руках / документ / новое появление

подробные object crops.

### По запросу

дополнительная ретроспективная обработка оригинальных изображений.

---

# 20. OCR

OCR является отдельным поисковым каналом.

Он особенно важен для:

* документов;
* упаковок;
* этикеток;
* коробок;
* писем;
* чеков;
* страховых полисов.

Система не обязана идеально прочитать один кадр.

OCR объединяется на уровне эпизода.

Например:

```text
кадр A:
"страх..."

кадр B:
"полис..."

кадр C:
"Toyota"

↓
combined OCR episode
```

---

# 21. OCR index

Необходимо хранить:

```text
raw_ocr_text
normalized_ocr_text
ocr_embedding
confidence
language
```

Индексировать текст двумя способами:

* full-text search;
* semantic text embeddings.

# 24. Долговременное происхождение предмета

Для каждого устойчивого Object желательно иметь:

```text
first_seen

first_context

possible_acquisition

initial_placement

last_seen

sightings[]
```

Например:

```text
Object #8172
белая канистра с синей крышкой

first_seen:
2025-04-12 18:17

possible_acquisition:
принесена домой в пакете

initial_placement:
кладовка, нижняя полка

last_seen:
2026-09-09 10:41
```

Поздние случайные наблюдения не должны перезаписывать происхождение объекта.

---

# 25. Lazy event reconstruction

Не нужно пытаться полностью понимать все события во время ежедневного ingestion.

Большая часть сложного анализа выполняется **по запросу**.

Например:

> «Откуда появилась эта канистра?»

Pipeline:

```text
текущий crop канистры
↓
instance/semantic search
↓
поиск совпадений за 2 года
↓
поиск самого раннего уверенного кластера
↓
извлечение ± нескольких минут
↓
анализ последовательности
↓
VLM при наличии интернета
```

Это существенно экономит вычисления и API.

---

# 26. Класс запросов: WHERE

Пример:

> «Где моя отвёртка с жёлтой ручкой?»

Pipeline:

```text
speech/text
↓
query embedding
↓
visual retrieval
↓
Top-N frames
↓
temporal grouping
↓
последний релевантный эпизод
```

Ответ без VLM:

> Последнее уверенное изображение — сегодня в 17:43 возле рабочего стола.

---

# 27. Класс запросов: WHERE DID I PUT

Пример:

> «Куда я положил отвёртку?»

Нужно найти:

```text
предмет виден
↓
предмет в руке
↓
перемещение
↓
предмет исчез
```

И анализировать временную последовательность.

Пример ответа:

> Похоже, вы положили отвёртку во второй ящик шкафа около 17:44.

---

# 28. Класс запросов: WHERE DID IT COME FROM

Пример:

> «Откуда появилась эта вещь?»

Поиск идёт назад во времени.

Необходимо найти:

* первое уверенное появление;
* событие непосредственно перед появлением;
* контейнер;
* помещение;
* перенос.

Пример:

> Впервые этот предмет уверенно виден 12 апреля 2025 года. Вы достали его из пакета после возвращения домой и поставили в кладовку.

---

# 29. Класс запросов: ACQUISITION

Пример:

> «Когда я купил эту канистру?»

Система должна различать:

**факт** и **предположение**.

Если видна касса/магазин/чек:

> Вероятно, куплена 12 апреля около 17:50.

Если видно только появление дома:

> Она впервые появляется в записях после вашего возвращения домой 12 апреля. Сам момент покупки не зафиксирован.

Запрещено выдавать предположение за подтверждённый факт.

---

# 30. Документные запросы

Пример:

> «Куда я положил документы на сад?»

Query planner генерирует несколько направлений поиска.

### Visual

```text
documents
papers
folder
envelope
```

### OCR

```text
сад
участок
земельный
кадастр
собственность
адрес участка
договор
```

### Semantic text search

Ищутся OCR-фрагменты, семантически связанные с запросом.

После объединения кандидатов анализируется временной контекст.

---

# 31. Голосовой интерфейс

Основной способ запроса — голос.

Пользователь:

```text
нажал большую кнопку
↓
произнёс вопрос
↓
получил ответ
```

Интерфейс не должен требовать знания:

* embeddings;
* OCR;
* временных фильтров;
* названий моделей.

---

# 32. Контекст диалога

Система должна поддерживать ссылочные запросы.

Пример:

> Где жёлтая отвёртка?

Ответ.

Затем:

> А откуда она появилась?

Система должна понимать, что «она» относится к найденной отвёртке.

---

# 33. Указание предмета через изображение

Поддержать:

### Тап по объекту

Пользователь открывает кадр и нажимает на предмет.

### Текущая камера

Пользователь показывает предмет:

> «Откуда это?»

Система получает crop объекта и ищет его историю.

---

# 34. VLM

VLM не используется для анализа десятков тысяч кадров ежедневно.

Она используется как reranker/reasoner.

Пример:

```text
vector search
↓
100 кадров
↓
temporal clustering
↓
5 эпизодов
↓
30–60 релевантных кадров
↓
VLM
```

---

# 35. Требования к VLM prompt

Модель должна получать инструкции:

* не фантазировать;
* разделять факт и предположение;
* указывать confidence;
* говорить, если данных недостаточно;
* анализировать последовательность во времени;
* учитывать timestamps.

Пример результата:

```text
hypothesis:
объект был извлечён из верхнего ящика

confidence:
0.82

evidence:
17:41:12
17:41:16
17:41:21
```

---

# 36. Работа без VLM

Если интернет отсутствует:

система не должна выдавать ошибку.

Она должна дать базовый retrieval-result:

> Последнее уверенное появление предмета — вчера в 18:43.

И показать несколько кадров.

---

# 37. Evidence-first UI

Любой вывод системы должен позволять открыть исходные доказательства.

Ответ:

> Похоже, ключи были положены в верхний ящик.

Ниже:

```text
[18:42:17]
[18:42:20]
[18:42:23]

Показать весь эпизод
```

Пользователь может проверить вывод самостоятельно.

---

# 38. История на 1–2 года

Поиск должен поддерживать многолетний архив.

Индекс рекомендуется партиционировать по времени:

```text
2026-01
2026-02
...
2027-01
```

или аналогичным способом.

Запрос «где сейчас?» преимущественно работает с новыми partition.

Запрос «откуда появилась?» может выполнять поиск назад во времени.

---

# 39. Оценка объёма исходных изображений

При 16 часах записи:

### Каждые 5 секунд

~11 520 кадров/сутки.

### Каждые 2 секунды

~28 800 кадров/сутки.

Если JPEG в среднем занимает 300 КБ:

при 2 сек:

```text
~8.6 ГБ/сутки
~260 ГБ/месяц
~3.1 ТБ/год
```

Фактический размер должен быть измерен на A33.

---

# 40. Требования к серверной производительности

Базовая цель:

полный дневной объём должен обрабатываться быстрее, чем появляется следующий дневной объём.

Для 28 800 кадров:

**обработка должна укладываться в ночь.**

Минимальный target:

> весь день обработан за ≤8 часов.

Желательный:

> ≤2–4 часов.

# 52. Отказоустойчивость

Система должна переживать:

### Пропал Wi-Fi

Upload продолжается позже.

### Сервер выключен

Телефон хранит локальную очередь.

### Перезагрузился телефон

Запись/очередь корректно восстанавливаются.

### Перезагрузился сервер

Processing jobs не теряются.

### Повторная загрузка

Дубликаты не создаются.

### Повреждён файл

Запрашивается повторная передача.

# 56. Основные критерии качества поиска

Необходимо создать собственный benchmark.

Например, 100 специально записанных бытовых событий:

* отвёртка;
* ключи;
* ножницы;
* очки;
* папка;
* коробка;
* документы;
* канистра;
* пульт;
* мелкие инструменты.

Проверять:

```text
Recall@5
Recall@20
Recall@100
```

---

# 57. Основной критерий visual retrieval

Для запроса:

> «жёлтая отвёртка»

правильный эпизод должен попадать в Top-20.

Начальный целевой уровень:

**Recall@20 ≥ 90% для хорошо видимых бытовых предметов.**

Для очень мелких/частично закрытых объектов допустимо отдельно измерять качество.

---

# 58. Критерий capture quality

Для искусственно поставленных событий:

```text
взял предмет
↓
перенёс
↓
положил
```

минимум один пригодный для анализа кадр ключевого действия должен присутствовать в подавляющем большинстве эпизодов.

Целевой уровень:

**≥95% тестовых событий.**

Если этот показатель низкий, улучшение ML не решит проблему — надо менять режим съёмки или крепление камеры.

---

# 59. Критерий provenance

При наличии в архиве события:

```text
принёс предмет
↓
достал из пакета
↓
положил
```

запрос:

> «Откуда появилась эта вещь?»

должен находить соответствующий ранний эпизод.

Не обязательно автоматически доказать факт покупки.

Главное — найти первичный контекст.

---

# 60. Главные ограничения системы

Система физически не может восстановить событие, которое камера не видела.

Если предмет:

* принесли без камеры;
* положили вне поля зрения;
* кадр был полностью смазан;

система должна честно сообщить:

> Происхождение по имеющимся записям определить не удалось.

---

# 61. Запрещённое поведение

Система не должна:

* придумывать местонахождение;
* придумывать факт покупки;
* выдавать вероятностный вывод за факт;
* скрывать неопределённость;
* удалять исходные данные до подтверждённой синхронизации.

# 71. Конечная философия системы

Система строится не вокруг модели:

> «ИИ посмотрел все фотографии и всё понял».

Она строится вокруг модели:

> **«Мы надёжно сохранили историю, построили хорошие индексы и можем восстановить нужный эпизод тогда, когда он понадобился».**

Это позволяет:

* хранить историю годами;
* использовать новые модели для старых данных;
* не зависеть от облака;
* не тратить API на миллионы кадров;
* постепенно улучшать качество системы без замены носимого устройства.

# 72. Итоговое распределение обязанностей

## Samsung A33

**Capture layer**

Должен:

* снимать;
* сохранять;
* не терять данные;
* передавать их серверу;
* принимать голосовые запросы;
* отображать результаты.

---

## Домашний сервер

**Memory + retrieval layer**

Должен:

* хранить многолетний архив;
* рассчитывать embeddings;
* выполнять OCR;
* индексировать данные;
* находить предметы;
* восстанавливать временной контекст;
* хранить provenance;
* предоставлять локальный Search API.

---

## VLM API

**Reasoning layer**

Должна:

* анализировать небольшое число релевантных кадров;
* понимать последовательность действий;
* выбирать наиболее вероятную гипотезу;
* генерировать понятный ответ;
* явно указывать неопределённость.

Она не является обязательной для базовой работы системы.
